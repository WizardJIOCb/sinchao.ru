# Подготовленная онлайн-оплата счёта за столом

Интеграция ЮKassa подготовлена для карты и СБП через размещённую у провайдера страницу. В текущем развёртывании она выключена: реквизиты магазина и секретный ключ не настроены. Гость может получить счёт и оплатить официанту; переход на настоящую оплату не показывается как доступный.

## Что оплачивается

Гость сначала присоединяется к открытому посещению через QR стола и выданный сотрудником код. Для оплаты нужна уже сформированная часть счёта (`bill_shares`): одна часть — весь счёт, несколько — равное разделение. Платёж покрывает серверный остаток этой части: сумма вместе с чаевыми минус ранее применённый сертификат. Клиент передаёт только способ оплаты, без суммы, валюты, URL возврата или ключей ЮKassa.

Для СБП поддерживается диапазон от 1 до 700 000 ₽ включительно. Остаток меньше рубля после сертификата или сумма сверх лимита отклоняются до создания попытки и обращения к провайдеру; оплатить официанту по-прежнему можно.

Пока счёт разделён, дозаказы блокируются существующим правилом счёта. Пока онлайн-платёж создаётся или ожидает результата, для этой части также нельзя подтвердить наличные или потратить сертификат; нельзя сбросить разделение и закрыть посещение. Так ресторан не получает два списания за один счёт. Другая неоплаченная часть того же счёта может оплачиваться отдельно.

После подтверждённого успеха часть отмечается оплаченной. Когда оплачены все части, все неотменённые заказы посещения получают `payment_status=PAID`. Завершение кухни, начисление бонусов и закрытие визита сохраняют действующий порядок. В журнале фиксируется `BILL_SHARE_PAID_ONLINE`, гость получает уведомление; эти записи не являются фискальным чеком.

## Настройки перед активацией

Все настройки хранятся только на сервере в защищённом файле окружения; ключ не должен попадать в браузер, репозиторий или журнал:

| Переменная              | Значение                                                                                                                                      |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `YOOKASSA_ENABLED`      | Только `true` включает проверку остальных настроек; отсутствие/любое другое значение выключает оплату.                                        |
| `YOOKASSA_SHOP_ID`      | Числовой идентификатор согласованного магазина ЮKassa.                                                                                        |
| `YOOKASSA_SECRET_KEY`   | Секретный ключ этого магазина.                                                                                                                |
| `APP_ORIGIN`            | Точный HTTPS origin сайта, без дополнительных путей и параметров.                                                                             |
| `YOOKASSA_RECEIPT_MODE` | Для реализованного сценария только `external`. Явное подтверждение согласованного рестораном внешнего процесса фискализации.                  |
| `YOOKASSA_TEST_MODE`    | По умолчанию `false`. `true` допустим только с отдельной БД, имя которой заканчивается на `_test`; sandbox не может оплатить настоящие счета. |

Режим ресторана `demo=true` дополнительно блокирует создание платежей настоящими деньгами и делает конфигурацию оплаты недоступной. Даже после выключения demo нельзя оплачивать реальные деньги за старые заказы, сохранённые как тестовые. Проверка уже начатого платежа остаётся доступна, чтобы изменение demo не потеряло поступившую оплату.

Перед включением нужны подключённый магазин, разрешённые карта/СБП, согласованный процесс чека, HTTPS webhook, проверка тестового магазина на отдельной БД и затем отдельно санкционированная проверка реальной оплаты. Настройки сами по себе не подтверждают работоспособность эквайринга. В рамках этой доработки реальные реквизиты не вводились и деньги не списывались.

### Фискальные чеки

Реализован сценарий с внешней онлайн-кассой/процессом ресторана. API не передаёт объект `receipt` в ЮKassa и не изображает общую часть счёта фиктивной товарной строкой. Разделённый счёт, сертификат, скидки и чаевые требуют согласованного распределения товарных позиций и фискальных сумм. Внешний процесс должен учитывать подтверждённые оплаты из журнала, выпускать и доставлять корректный чек; его автоматизация не реализована этой интеграцией.

Если ресторан хочет формировать чеки силами ЮKassa, сначала нужно реализовать товарное распределение и настройки фискализации, получение контакта для чека и проверку его регистрации. Значение `YOOKASSA_RECEIPT_MODE=external` нельзя использовать вместо реально подготовленного процесса чека.

## API и проверка результата

Маршруты клиента под `/api/payments` требуют обычную сессию. Маршруты конкретного визита доступны только его участникам:

- `GET /config` — доступность, способы и сообщение без реквизитов.
- `POST /visits/:id/shares/:shareId` с `{ "method": "bank_card" }` или `{ "method": "sbp" }` — начать или продолжить существующую попытку.
- `GET /visits/:id/payments` — сохранённые попытки и текущие серверные статусы.
- `POST /visits/:id/payments/:paymentId/sync` — запросить статус через серверный API ЮKassa.

Статусы: `CREATING`, `PENDING`, `WAITING_FOR_CAPTURE`, `SUCCEEDED`, `CANCELED`. Режим `capture=true` использует одностадийное списание; неожиданный `WAITING_FOR_CAPTURE` блокирует оплату наличными и требует сверки оператора. Автоматического capture и возврата не реализовано.

До сетевого запроса создаётся долговечная запись платежа с отдельным `provider_key`, идентификатором исходного магазина и режимом test. Повторные и параллельные запросы возвращают ту же запись и используют тот же ключ провайдера. Смена магазина или test-режима блокирует повторные обращения по старой попытке, чтобы она не создалась заново в другом магазине. При потере сетевого ответа попытка остаётся активной. Идентификатор ЮKassa сохраняется до последующей проверки GET; затем проверяются идентификатор, магазин получателя, сумма до копейки, RUB, способ, режим `test`, metadata, `paid` и статус. Списание засчитывается только после авторитетного GET с `succeeded` и `paid=true`, в транзакции с блокировками визита и части счёта. Повторные события не начисляют оплату или уведомление второй раз.

URL возврата формируется сервером: `APP_ORIGIN/dine-in/<table-token>?payment=<intent-id>`. Параметр `payment` служит только подсказкой интерфейсу для проверки. Возврат в браузер и содержимое webhook не доказывают оплату. `confirmation_url` должен быть HTTPS на домене `yookassa.ru` или `yoomoney.ru` (включая их поддомены), без встроенных логина/пароля и нестандартного порта.

В личном кабинете ЮKassa подпишитесь на `payment.succeeded`, `payment.canceled`, `payment.waiting_for_capture` по адресу `https://sinchao.ru/api/payments/yookassa/webhook`. Маршрут не создаёт гостевую сессию и принимает событие только как повод проверить известную попытку через API. Неизвестные платежи игнорируются. Ошибка проверки не подтверждается HTTP 200, чтобы провайдер мог повторить доставку.

## Сбой и сверка

При временной ошибке используйте «Проверить оплату»/повтор создания: сервер продолжит прежнюю попытку. Не подтверждайте наличные, если посетитель уже прошёл форму провайдера, а статус ещё неизвестен. После авторитетного `canceled` доступна оплата официанту или новая попытка. Отменённые записи сохраняются, включая исходный идентификатор части даже после сброса неоплаченного разделения.

ЮKassa гарантирует идемпотентность ключа 24 часа. Если идентификатор провайдера так и не получен, спустя 23 часа сервер прекращает повтор POST: новый запрос после истечения срока мог бы списать деньги ещё раз. Сотрудник должен найти попытку в личном кабинете ЮKassa по metadata и сверить её через API; автоматически отпускать блокировку по таймеру нельзя. Сохранённые попытки с идентификатором можно продолжать проверять GET без этого ограничения. Автоматизированный интерфейс ручной сверки старых неизвестных попыток и возвраты — отдельная доработка.

## Проверки

`tests/online-payments.test.ts` использует отдельную `_test` БД и подменённый транспорт ЮKassa. Он проверяет отсутствие провайдера, demo gate, авторизацию, сумму после сертификата с чаевыми, проверку валюты/metadata/магазина/test/URL, параллельные повторы, потерянный сетевой ответ, защиты от наличных/сертификата/сброса/закрытия, поддельное событие, повторную успешную доставку и снятие блокировки после проверенной отмены. Реального обращения к ЮKassa и реальной оплаты в этих тестах нет.
